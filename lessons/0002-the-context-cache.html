Lesson 0002 · 内存与算力瓶颈

上下文高速缓存：为什么大模型会“健忘”与“迷失”

从片上 RAM 到注意力矩阵：透视 Context Window 的物理代价与信息衰减。

一、 核心心智模型：Context 就是模型的片上 L3 Cache

在 Android 系统中，App 如果把海量对象无脑丢在内存中，会引发 GC 频繁停顿甚至 OOM；而在 LLM 的世界里，上下文窗口（Context Window）承担着完全相同的角色。

Context 的物理本质： 模型每一次预测下一个 Token 时，必须“同时注视”并计算上文中所有已存在的 Tokens。

这意味着：上下文不是免费的持久硬盘，而是极其昂贵、算力开销随长度剧增的动态工作缓存。

二、 Attention 的二次方开销与“迷失在中间”现象

1. 计算爆炸：O(N²) 的全连接注意力

在标准 Transformer 架构中，如果上文有 $N$ 个 Tokens，每个 Token 都要和其余所有 Token 做一次点积相关性计算（Self-Attention）。当你的上下文从 4K 膨胀到 64K 时，计算量不是增加 16 倍，而是增加 256 倍！这也是为什么超长上下文推理延迟急剧飙升、费用暴涨的原因。

2. 为什么它对中间的指令视而不见？（Lost in the Middle）

斯坦福大学的一项经典研究证实：大模型对位于 Context 开头（Prompt 首部）和结尾（最新输入）的信息召回率最高，而埋在长文本正中间的约束规则，注意力权重会断崖式衰减！

这就解释了你之前在用 Agent 时的切身体会：当你给它塞了一大堆错误日志、或者抓回了整整 50KB 包含混乱 HTML 的网页源码时，它不仅找不到关键按钮，还会突然把你一开始定好的规则给“忘”得一干二净！
